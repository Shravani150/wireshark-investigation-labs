# Case 02 – Follow a TCP Conversation

## Objective

Investigate a packet capture generated by:

```bash
curl http://example.com
```

and reconstruct the exact web request and response while separating it from unrelated background traffic.

---

## Scenario

A user accessed `http://example.com` using `curl`. The capture also contains other network activity from the operating system. The goal is to identify the correct conversation and explain what happened.

---

# Investigation Steps

## Step 1 – Capture Overview

### Total Packet Count

```
364 packets
```

### Protocols Observed

```
ICMPv6
ARP
DNS
QUIC
TCP
TLSv1.3
TLSv1.2
HTTP
PKIX-CRL
```

---

## Step 2 – Isolate HTTP Traffic

Apply the display filter:

```text
http
```

### Result

```
8 packets remain
```

---

## Step 3 – Identify the Relevant Request

### Packet Number

```
303
```

### Packet Summary

```
GET / HTTP/1.1
```

### Host Header

```http
Host: example.com
```

### Observation

The `Host` header confirms that this HTTP request was intended for **example.com**.

---

## Step 4 – Identify Unrelated Traffic

Earlier HTTP packets were observed:

```text
GET /we1/uCglcmwwftc.crl HTTP/1.1
Host: c.pki.goog
```

### Conclusion

These packets belong to Google certificate infrastructure traffic and are **not part of the example.com investigation**.

---

## Step 5 – Follow the Conversation

Action performed:

**Follow → TCP Stream**

### Client Request (Red)

```http
GET / HTTP/1.1
Host: example.com
User-Agent: curl/8.21.0
Accept: */*
```

### Observation

The HTTP request is visible in plain text because the connection uses **HTTP**, not HTTPS.

The same content returned by the server was also printed in the terminal by `curl`.

---

# Request Analysis

| Item          | Answer        |
| ------------- | ------------- |
| HTTP Method   | `GET`         |
| Path          | `/`           |
| Host          | `example.com` |
| HTTP Version  | `HTTP/1.1`    |
| Status Code   | `200 OK`      |
| Server Header | `cloudflare`  |

---

## Note About the Path

The path is taken from:

```http
GET / HTTP/1.1
```

The value `/` represents the **homepage (root path)** of the website.

The line:

```http
Host: example.com
```

identifies the website being requested and is **not** the path.

---

# Additional Observation

The response contained:

```http
Connection: keep-alive
```

This indicates that the TCP connection may remain open for a short time so additional HTTP requests can be sent without performing another TCP handshake, improving efficiency.

---

# Why "Follow HTTP Stream" and "Follow TCP Stream" Looked the Same

In this capture, the TCP connection carried only a single HTTP request and response. Therefore, both views displayed the same conversation.

---

# Investigation Workflow

This case demonstrates a practical packet-analysis workflow:

1. **Capture traffic**
2. **Filter for the relevant protocol (`http`)**
3. **Identify the target request (`Host: example.com`)**
4. **Ignore unrelated background traffic (`c.pki.goog`)**
5. **Follow the conversation**
6. **Reconstruct the user action**

This is the same reasoning process used in real network investigations.

---

# Key Learnings

* HTTP requests are readable in packet captures.
* The `Host` header identifies the target website.
* Packet captures often contain unrelated background traffic.
* Filtering is essential for isolating the correct conversation.
* Following a stream allows reconstruction of the full request and response.
* A user action can be rebuilt from packet data.

---

# Conclusion

The investigation successfully identified the HTTP conversation generated by:

```bash
curl http://example.com
```

The user requested the root page (`/`) of **example.com**, the server responded with **200 OK**, and the response was served by **Cloudflare**. Unrelated certificate-validation traffic was correctly identified and excluded from the investigation.
