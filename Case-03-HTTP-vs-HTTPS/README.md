# Case 03 - HTTP vs HTTPS Investigation

## Objective

Compare HTTP and HTTPS traffic generated by the same action and determine what information remains visible after TLS encryption is applied.

---

## Evidence

### HTTP Capture

`Case-02-HTTP.pcapng`

### HTTPS Capture

`lab1.pcapng`

---

## Investigation

### HTTP Analysis

#### Display Filter Used

```text
http
```

Because HTTP traffic is transmitted in plaintext, Wireshark can directly identify and decode the HTTP protocol.

#### Findings

| Item | Value |
|--------|--------|
| GET Request Packet | 303 |
| Method | GET |
| Host Header | example.com |
| User-Agent | curl/8.21.0 |
| HTML Content Visible | Yes |
| Follow TCP Stream | Readable |

---

### HTTPS Analysis

#### Display Filter Used

```text
tls
```

Unlike HTTP, HTTPS traffic is encrypted using TLS.

Because the HTTP request and response are encrypted, Wireshark cannot directly identify or display HTTP messages.

Instead, Wireshark displays TLS packets, which contain the encrypted HTTP data.

#### Findings

| Item | Value |
|--------|--------|
| Client Hello Packet | 230 |
| TLS Version | TLSv1.3 |
| SNI | example.com |
| GET Request Visible | No |
| HTML Content Visible | No |
| Follow TCP Stream | Encrypted |

---

## Protocol Visibility in Wireshark

One of the key observations from this investigation was how protocol visibility changes after encryption is introduced.

### HTTP

Filtering for:

```text
http
```

works because HTTP is transmitted in plaintext.

Wireshark can directly decode and display:

- HTTP Methods (GET, POST, etc.)
- Host Header
- User-Agent
- URL Path
- Response Headers
- HTML Content

---

### HTTPS

Filtering for:

```text
https
```

does not reveal the web request in the same way.

Instead, Wireshark primarily shows:

```text
tls
```

because the HTTP request and response are encrypted inside TLS.

The HTTP messages still exist, but they are protected by encryption and cannot be viewed without the appropriate TLS session keys.

As a result:

- GET requests are not visible
- URL paths are not visible
- User-Agent headers are not visible
- HTML content is not visible

However, some metadata remains observable.

---

## HTTP vs HTTPS Comparison

| Item | HTTP | HTTPS |
|--------|--------|--------|
| Destination IP Visible | Yes | Yes |
| Port Visible | Yes | Yes |
| Hostname Visible | Yes | Partially (via SNI) |
| HTTP Method Visible | Yes | No |
| URL Path Visible | Yes | No |
| User-Agent Visible | Yes | No |
| Page Content Visible | Yes | No |

---

## Key Observation

During the HTTP investigation, the complete request and response were visible and could be reconstructed using Follow TCP Stream.

During the HTTPS investigation, no readable HTTP request was visible because the HTTP data was encrypted inside TLS records.

This demonstrated that HTTPS protects the contents of communication, while some metadata such as IP addresses, ports, and the hostname (through SNI) may still remain visible.

---

## Investigation Workflow

1. Capture traffic.
2. Filter for the protocol of interest.
3. Identify the relevant request.
4. Ignore unrelated background traffic.
5. Follow the conversation.
6. Reconstruct the user action.

### Case 03 Example

```text
Capture Traffic
      ↓
Filter for HTTP or TLS
      ↓
Identify the relevant connection
      ↓
Inspect request visibility
      ↓
Compare HTTP vs HTTPS
      ↓
Determine what encryption hides
```

---

## Conclusion

A person on the same Wi-Fi network can still observe source and destination IP addresses, port numbers, connection timing, packet sizes, and often the hostname through TLS SNI.

However, the HTTP request, URL path, headers, and webpage content remain protected by TLS encryption and cannot be read from the packet capture alone.
